# AGENTS.md

Рабочий контекст для Codex и других агентов, которые вносят изменения в проект ALVISA SALARY.

## Проект

ALVISA SALARY - статическое фронтенд-приложение для сотрудников и руководителей отдела.

Основные сценарии:
- welcome-страница: `index.html`
- калькулятор зарплаты: `calculator.html` + `app.js`
- личный табель: `table.html` + `table.js`
- личный кабинет: `profile.html` + `profile.js`
- вход/регистрация/reset password: `login.html` + `login.js`
- owner-панель отделов: `owner.html` + `owner.js`
- общий табель отдела: `admin.html` + `admin.js`
- owner-центр пользователей: `owner-users.html` + `owner-users.js`
- owner-аналитика выплат: `owner-analytics.html` + `owner-analytics.js`
- owner-центр предложений: `owner-ideas.html` + `owner-ideas.js`
- общий верхний header/nav: `nav.js`

Стек:
- HTML
- Tailwind CSS 3.4 собирается локально из `styles/tailwind-input.css` в `styles/tailwind.css`; CDN не использовать
- vanilla JavaScript, ES modules
- Supabase JS client
- Supabase Auth
- Supabase Postgres / RPC / Realtime
- без React, без сборщика, без TypeScript

## Как работать с кодом

- Работать прямо в папке проекта, не создавать копии проекта на другом диске.
- Изменения делать точечно и совместимо с текущей архитектурой.
- Не ломать существующие `id` DOM-элементов, навигацию и структуру сохраненных данных без крайней необходимости.
- Общие запросы к Supabase добавлять в `db.js`, а не размазывать по page scripts.
- Общую логику выносить в отдельные небольшие ES modules только если она реально используется на нескольких страницах.
- Для SQL давать готовый скрипт в ответе. Пользователь сам запускает его в Supabase SQL Editor.
- SQL-скрипты сохранять в `supabase-sql/`, чтобы пользователь мог копировать их оттуда и чтобы история БД-изменений оставалась в репозитории.
- Предпочитать idempotent SQL: `create table if not exists`, `create index if not exists`, `create or replace function`, `do $$ begin ... end $$`.
- Не использовать `drop` в SQL без явной причины: Supabase показывает предупреждения о destructive operations.

- основной фон `#0b0d0f`, панели `#15191d`, светлый текст `#f1eee8`
- винный акцент `#7a1638`, стальной `#6ea8e8`, золотой `#c6a15b`

- плотные рабочие интерфейсы без декоративных карточек внутри карточек
- общие header и footer из `nav.js` и `footer.js`
- мягкие короткие hover-эффекты без сдвига рабочей компоновки

- Bootstrap-like админку
- резкие контрастные блоки
- React-style переписывание интерфейса
- большие рефакторинги ради маленьких задач
- фиолетово-синие градиенты, светящиеся фоновые сферы и старые квадратные знаки с буквой `A`
- возвращать крупные `rounded-2xl` / `rounded-3xl` без требования конкретного компонента

Верхняя шапка вынесена в `nav.js`.

Для страниц с общей шапкой в HTML должен быть placeholder:

```html
<div data-app-header data-active="table"></div>
<script type="module" src="./nav.js"></script>
```

Для owner-страниц, где нужны пункты "Отделы" и "Онлайн":

```html
<div data-app-header data-active="owner" data-owner-nav="true"></div>
```

Новые пункты верхнего меню добавлять в `nav.js`, а не вручную в каждую HTML-страницу.

Общая шапка в `nav.js` учитывает `env(safe-area-inset-top)` на iPhone. Страницы с обычной компоновкой используют `pt-safe`, а отдельные shell-контейнеры вроде `admin.html` — класс `app-header-offset`; не задавать для них независимый верхний отступ без учёта safe area.

Основное меню сотрудника: калькулятор, личный табель, смены, чек-лист смены, профиль. Страница новостей доступна из профиля и не дублируется в общем header.

Личный чек-лист смены находится в `checklist.html` + `checklist.js`; чистая логика шаблонов и прогресса — в `shiftChecklist.js`. Одновременно у пользователя может быть только одна активная смена. Список хранится в `shift_checklists` и доступен клиенту только через authenticated RPC из `032_shift_checklists.sql`; прямые права на таблицу не выдавать. Завершенные чек-листы являются постоянной историей для будущей статистики и не должны автоматически удаляться или перезаписываться. Push-напоминания раз в три часа отправляет защищенная функция `send-shift-checklist-reminders`, вызываемая cron раз в 15 минут. После нажатия «Смену сдал» напоминания обязаны прекращаться.

После завершения чек-листа серверная логика из `034_shift_handover_notifications.sql` определяет следующую смену по дневным и ночным часам табеля. Дневная смена уведомляет ночную на той же дате, ночная — дневную на дате окончания ночной смены. Руководящие должности, отсутствующие сотрудники и дни без следующей смены исключаются. Получателей нельзя вычислять или передавать с клиента.

Экспорт открытого месяца личного табеля в календарь реализован в `calendarExport.js`. Не указывать точное время для неоднозначной восьмичасовой смены: в разных отделах и ситуациях те же 8 часов могут означать разные интервалы. Комментарий к смене должен попадать в описание календарного события.

Интерактивное обучение заполнению табеля находится в `timesheet-training.html` + `timesheet-training.js`. Курс руководителя реализован отдельно в `manager-training.js`, но отображается на той же странице только для owner и пользователей из `department_editors`. Учебные данные не сохраняются в Supabase: прогресс сотрудника хранится под ключом `alvisa.timesheetTraining.v1`, прогресс руководителя — `alvisa.managerTraining.progress.v1:{user_id}`, а освоенные темы и результаты — `alvisa.timesheetTraining.result.v2:{user_id}`. Финальный шаг курса сотрудника выбирается случайно из банка экзаменационных сценариев, а проверка должна объяснять ошибки понятным языком. Старый Driver.js-тур остаётся обзором элементов реальных страниц, а не практикой заполнения.

Чат, голосование, задачи отдела, инструкции ЕГАИС, мини-игра и Excel-выгрузка полностью удалены как невостребованные функции. Не возвращать их страницы, клиентские API, ассеты или таблицы без нового явного решения пользователя. Удаление серверных объектов выполняет `036_remove_unused_features.sql`.

## Авторизация и роли

Авторизация через Supabase Auth.

Основные helper-функции:
- `auth.js`: `getSession`, `requireSession`, `signUp`, `signIn`, `signOut`, `verifyCurrentPassword`, `requestPasswordReset`, `updateMyPassword`
- `db.js`: `getMyProfile`, `updateMyProfile`, `updateMyProfileFields`, функции табелей, отделов и owner-RPC

Роли:
- `user` - обычный сотрудник
- `owner` - владелец системы, значение в `profiles.role`
- department editor - отдельная сущность в `department_editors`, не значение `profiles.role`

Owner-страницы должны проверять:
1. `requireSession()`
2. `getMyProfile()`
3. `profile.role === "owner"`

Редактор отдела может управлять конкретным общим табелем, но не всей системой.

Обычные сотрудники отдела ЕГАИС могут открывать общий график отдела через `admin.html?department=egais`, но только в режиме просмотра. Данные для этого режима загружаются через безопасный RPC из `030_egais_department_timesheet_view.sql`: не расширять обычные RLS-политики чтения табелей и не отдавать сотрудникам чужие оклады, `moneySnapshot` или `paySummary`.

Бета-расчёт предполагаемых отпускных находится в `vacationPay.js`. Он использует подтверждённую фактическую зарплату на руки за 12 календарных месяцев перед месяцем отпуска, исключает отдельные выплаты за отпуск / учёбу / больничный и уменьшает знаменатель для неполностью отработанных месяцев по формуле с коэффициентом `29.3`. Если точный расчётный период ещё не подтверждён целиком, допускается явно подписанный приблизительный расчёт по последним 12 подтверждённым месяцам. Не заменять эту логику подгоночным коэффициентом под одну выплату.

## Расчеты зарплаты и табеля

Главная формула: `calc.js`.

Константы:
- `BONUS_RATE = 0.35`
- `TAX_RATE = 0.13`
- `NIGHT_EXTRA_RATE = 0.4`

Бизнес-правила:
- оклад делится на норму часов
- премия 35%
- ночные дают +40% к базовой часовой ставке
- налог 13%
- праздники считаются отдельно как двойная оплата
- вредность для грузчика: +4%
- стандартная дневная норма: 8 часов
- женская дневная норма 7.2 применяется только для филиала `chateau_alvisa` / CHATEAU ALVISA; во всех остальных филиалах используется стандартная 40-часовая неделя
- лимит переработки за год: до 01.09.2026 используется 120 часов; с 01.09.2026 можно использовать 240 часов только при наличии основания в коллективном договоре или отраслевом соглашении
- если есть сохраненный `moneySnapshot`, он приоритетнее текущего оклада
- подтвержденные фактические суммы важнее авторасчета в годовых итогах

Коды табеля:
- `ОТ` - оплачиваемый отпуск
- `ОД` - отпуск без оплаты
- `ОЗ` - обязательный отпуск без оплаты
- `Б` - больничный
- `У` - учебный отпуск
- `УД` - учебный отпуск без оплаты
- `НТ` - не трудоустроен в этот день; уменьшает личную норму на норму конкретного рабочего дня, но не относится к оплачиваемым отсутствиям
- `УВ` - увольнение; не меняет норму само по себе, но блокирует заполнение дальнейших дней сотрудника в текущем и последующих табелях

Обязательные поля профиля для доступа к табелю:
- `display_name`
- `position`
- `gender`
- `oklad`

## Деньги и приватность

Денежные данные могут скрываться PIN-защитой.

Связанные поля:
- `profiles.hide_money`
- `profiles.money_pin_hash`
- `profiles.money_pin_salt`

Связанные файлы:
- `moneyPrivacy.js`
- `profile.js`
- `table.js`
- `app.js`
- `settings.js`

При изменениях не обходить PIN-логику и не показывать оклад/выплаты там, где они должны быть скрыты.

Годовой beta-прогноз повышенной оплаты находится в `yearEndReserve.js` и показывается только в карточке декабря в профиле. Он не должен менять обычный расчет в `calc.js` или ежемесячные суммы табеля.

Правила прогноза:
- используется предположение о годовом суммированном учете; это явно сообщается пользователю
- праздничные часы исключаются из сверхурочных, чтобы не оплачивать их повышенно дважды
- первые 2 часа годовой переработки дают дополнительную половину ставки, последующие часы - дополнительную полную ставку
- предварительная доля отложенной праздничной части равна 50%, но может уточняться по подтвержденным месяцам с праздниками
- результат называется прогнозом/ориентиром, а не доказанной задолженностью работодателя
- перед показом обязательно применять существующую PIN-защиту денежных данных

## Должности пользователя

`profiles.position` хранит как системные коды из списка, так и пользовательское текстовое название длиной до 80 символов. Клиент обязан нормализовать пробелы и отклонять управляющие символы и знаки `<`, `>`, `{`, `}`.

Выбор отдела в окне пользовательской должности не должен самовольно добавлять человека в `department_members`, назначать редактором или выдавать доступ к табелю. Состав отделов и права по-прежнему меняются только через защищенные owner/editor операции.

- `db.js`: `upsertMyPresence`, `ownerListUsers`

Отдельной owner-страницы только для онлайн-пользователей больше нет. Онлайн-фильтр находится в owner-центре пользователей.

Heartbeat вызывается на основных страницах после проверки сессии:
- `calculator.html` / `app.js`
- `profile.html` / `profile.js`
- `table.html` / `table.js`
- `settings.html` / `settings.js`
- `admin.html` / `admin.js`
- `owner.html` / `owner.js`
- `owner-users.html` / `owner-users.js`
- `owner-analytics.html` / `owner-analytics.js`

Ошибки heartbeat не должны ломать страницу: если таблица/RPC еще не созданы или сессии нет, страница должна продолжать работать.

## Зафиксированные продуктовые решения

Без нового прямого запроса пользователя не предлагать:
- журнал изменений табеля: при появлении руководителя или редактора обычные сотрудники лишаются права менять табель, поэтому отдельный журнал сейчас не оправдан;
- отдельную кнопку отмены последнего действия: для текущего сценария достаточно работающего `Ctrl+Z`;
- автоматическое составление или заполнение графика.

Допустимые направления улучшений:
- локальный кеш графика только для чтения; при недоступной базе обязательно показывать явное сообщение: «Нет доступа к базе, показан последний загруженный график», дату обновления и запрещать отправку кешированных данных как новых;
- аудит доступности и постепенная унификация компонентов без ухудшения действующего дизайна;
- дальнейшее ужесточение CSP после выноса оставшихся inline-скриптов и автоматические проверки RLS вне пользовательского сайта;
- журналировать только существенные программные ошибки, исключая обычные сетевые сбои, отсутствие VPN, отмененные запросы и плохое соединение;
- ревизия старого кода с проверкой фактических связей перед удалением;
- виртуализацию строк админ-табеля рассматривать только при подтвержденных проблемах производительности и с сохранением клавиатурной навигации, sticky-элементов и drag-and-drop.

Реализованная техническая база:
- `uiStatus.js` унифицирует визуальные и доступные состояния загрузки, сохранения и ошибок;
- `scheduleCache.js` хранит только двухдневный график для чтения, отдельно по пользователю, отделу и дате, не дольше 14 дней;
- Tailwind собирается командой `npm run build:css`; сгенерированный `styles/tailwind.css` должен попадать в Git;
- все HTML-страницы содержат базовую CSP; при добавлении внешнего ресурса сначала проверить и минимально расширить соответствующую директиву;
- `errorLogger.js` отправляет только ограниченное число существенных ошибок через RPC из `035_client_error_logging.sql`; сетевые ошибки и отсутствие VPN не журналируются;
- `.github/workflows/quality.yml` запускает локальную сборку CSS и регрессионные тесты без нагрузки на пользовательский сайт.

## Ближайшие идеи / backlog

- Админ-табель: быстрый поиск сотрудника, фильтры "только с переработкой", "только с ошибками", "только незаполненные", более заметные статусы сохранения. Это приоритетная будущая полировка для руководителей.

## Журнал обновлений

Файл: `updates.html`.

Если пользователь после крупных изменений просит обновить журнал изменений, добавлять информацию в блок "Что уже добавлено":

```html
<div class="mt-4 grid gap-3 text-sm text-slate-300/90 leading-6">
```

Добавлять только пользовательски значимые изменения: новые возможности, изменения поведения, UX, безопасность, табель, профиль, чат, калькулятор. Не описывать внутренние технические работы, которые пользователю не важны, например мелкие правки owner/admin-логики, рефакторинг, перенос кода или SQL-служебку без видимого эффекта.

Текст писать простым русским языком в стиле существующих пунктов:

```html
<div>• Добавлена возможность ...</div>
```

Если изменение касается только owner/admin и обычным сотрудникам знать об этом не нужно, не добавлять его в `updates.html`, если пользователь явно не попросил.

При публикации нового пользовательского обновления менять `CURRENT_UPDATES_VERSION` в `nav.js`. Страница `updates.html` отмечает текущую версию прочитанной локально, а авторизованному пользователю, который ее еще не открывал, показывается одно напоминание за сеанс браузера.

## Проверка изменений

Для JS-файлов:
- `node --check file.js`

Для diff:
- `git diff --check`
- `git status --short`

Если пользователь просит "комить", "commit", "пуш" или "push" без дополнительных условий, выполнять стандартную схему из корня проекта:

```powershell
git add .
git commit -m "Короткое сообщение по смыслу изменений"
git push
```

Если пользователь явно указал текст коммита, использовать его. Если текст не указан, выбрать короткое русское сообщение по сути внесенных изменений.

Проект можно открывать через Visual Studio Live Server. Для быстрой локальной проверки можно поднять простой сервер из корня проекта:

```powershell
python -m http.server 5501 --bind 127.0.0.1
```

Не открывать ES modules напрямую через `file://`, лучше использовать локальный сервер.
