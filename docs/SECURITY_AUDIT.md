# Безопасность ALVISA SALARY

Актуальные ограничения и проверки для статического клиента, Supabase RLS/RPC, Storage и Edge Functions.

## Обязательные правила

- Права проверяются сервером; скрытая кнопка не является защитой.
- Изменение роли, отделов, чужих табелей и owner-операции выполняются только через защищенные RPC или Edge Functions.
- Service-role, приватный VAPID-ключ, пароли и `CRON_SECRET` не попадают в клиентский код и Git.
- Пользовательские строки выводятся через `textContent`; переходы и URL проверяются по разрешенным origin и схемам.
- Аватары ограничены папкой пользователя, разрешенными форматами и размером.
- Табель проверяется сервером: корректный период, размер payload, допустимые коды и не более 24 часов в сутки.
- Денежный PIN защищает только от случайного просмотра на открытом устройстве и не заменяет пароль аккаунта.
- Клиентский журнал исключает сетевые сбои, отсутствие VPN и отмененные запросы.

## Проверка базы

После новых миграций безопасности запускать актуальный отчет `027_security_audit_report.sql` и проверять:

- `authenticated` не может менять `profiles.role`;
- обычный сотрудник не читает чужой профиль и табель;
- редактор управляет только разрешенным отделом;
- owner RPC и административные Edge Functions недоступны остальным;
- у `anon` и `authenticated` нет лишнего доступа к `security definer` функциям;
- загрузка в чужую папку аватаров запрещена.

Перед потенциально разрушительной миграцией делать резервную копию. Активные нагрузочные и разрушающие проверки на рабочей базе без отдельного решения не выполнять.

## Усиление Owner-доступа

Миграция `066_owner_access_hardening.sql` повторно ограничивает grants профиля,
добавляет restrictive RLS поверх старых политик и отдельный триггер неизменности
UID, роли и даты создания. Изменение роли через клиент запрещено даже владельцу;
назначение owner остаётся административным действием через SQL/service-role.
Редакторы получают поля сотрудников своего отдела через защищённый
`list_managed_department_members`, без PIN-хешей и настроек защиты. Прямое чтение
чужих профилей ограничено владельцем. До установки SQL клиент сохраняет старый
запрос только при отсутствии нового RPC, но не при отказе в доступе.
Сохранение собственного профиля через upsert сохраняется. Служебные `_owner_*`
и `service_owner_*` RPC недоступны клиентам. Миграция прекращается с откатом,
если найдёт owner-функцию без ожидаемой проверки роли: такую функцию нужно
рассмотреть отдельно, а не автоматически разрешать.
Восемь исторических функций с префиксом `owner_` (создание, отзыв и удаление
приглашения, списки сотрудников/редакторов/доступных профилей, добавление и удаление
сотрудников отдела) сохраняют проверку `can_edit_department`:
ими законно пользуются редакторы своего отдела. Исключение задано точными
сигнатурами, не распространяется на прочие owner RPC. Схема `extensions`
остаётся в защищённом search_path, поскольку приглашения используют pgcrypto.
Старые `owner_add_department_editor` и `owner_remove_department_editor` теперь
проверяют именно `is_owner`: редактор не может делегировать права или снимать
права другого редактора. Прямая запись в `department_editors` с клиентским JWT
запрещена, включая старые колоночные grants. Определения старых функций проверены
по предоставленному отчёту рабочей БД и сохранены в тестовой фикстуре.
Старый `owner_remove_department_member` для редакторов делегирует удаление
защищённому `remove_managed_department_member`, чтобы нельзя было обходить
запрет на удаление себя, овнера или другого редактора через старый RPC.

В owner-интерфейсе пользовательские строки выводятся через `textContent`.
Аватары дополнительно проверяются на origin хранилища проекта и папку UID;
сторонние адреса, опасные схемы и обход пути отклоняются. Такая же проверка
добавлена в серверный триггер для новых/изменённых аватаров.

Миграция `067_owner_login_notifications.sql` создаёт уведомление и запись
в owner-журнале при новой сессии `auth.sessions`. Это работает и при обходе
нашей страницы входа. Обновление токена и открытие страницы не создают повторов.
Сообщение содержит серверное время по Москве, IP и ОС/браузер из User-Agent.
Город не определяется: IP может быть адресом VPN, User-Agent можно подменить.
Повторная проверка пароля, если Auth создаёт новую сессию, тоже даст уведомление.
Пароли, токены и идентификаторы сессий в уведомления/журнал не записываются.

Push проверяется каждую минуту заданием `alvisa-owner-login-push`, используя
существующие Vault-секреты напоминаний. Требуются активная подписка владельца,
развёрнутая обновлённая `send-push-notifications` и работающий cron. При отсутствии
cron/Vault уведомление внутри сайта всё равно создаётся; миграция выдаёт NOTICE.
Ошибка создания уведомления не блокирует вход, но фиксируется кодом в Postgres
logs. Проверять эту ошибку при диагностике отсутствующих уведомлений.

После применения запустить `068_owner_security_report.sql` и убедиться,
что проверки дают `true`, а списки проблемных функций пустые. Проверка прав
новых миграций выполнялась на локальном Postgres-движке PGlite, не на рабочей БД.
Без авторизации на рабочем API owner RPC не предоставили доступ; запрос профилей
не вернул строк. Это не заменяет проверку под обычной авторизованной учёткой.

Для повторного интеграционного теста установить PGlite вне проекта, задать
`PGLITE_MODULE` как file URL его `dist/index.js` и запустить
`node --test tests/owner-security.test.mjs tests/security-regression.test.mjs`.
Без этой переменной запускаются быстрые проверки, SQL-интеграция пропускается.

Источники формата Auth-сессии: [Supabase Auth](https://github.com/supabase/auth/blob/master/internal/models/sessions.go).

## Ограничения Проверки

- Статический анализ и локальные тесты не подтверждают фактические grants и RLS рабочего проекта; это проверяется SQL-отчетом в Supabase.
- Внешние библиотеки и шрифты, разрешенные CSP, остаются частью цепочки поставки. Новые внешние источники без необходимости не добавлять.
- Любой секрет, показанный в переписке, терминале или клиентском логе, следует заменить и далее хранить только в Supabase Secrets, Vault или менеджере паролей.

Связанные материалы: `SUPABASE_SQL.md`, `EDGE_FUNCTIONS.md`, `tests/security-regression.test.mjs`.
