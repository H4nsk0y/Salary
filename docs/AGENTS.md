# AGENTS.md

Краткий рабочий контекст для агентов, которые меняют ALVISA SALARY. Подробное описание проекта находится в корневом `README.md`, история БД - в нумерованных файлах `supabase-sql/`.

## Проект

ALVISA SALARY - статическое фронтенд-приложение для сотрудников и руководителей предприятия.

Стек:
- HTML и vanilla JavaScript с ES modules;
- Tailwind CSS 3.4, собранный локально;
- Supabase Auth, Postgres, RPC, Realtime и Edge Functions;
- Capacitor для Android;
- без React и TypeScript.

Основные маршруты:
- `index.html` - главная;
- `table.html` - личный табель;
- `admin.html` - общий табель отдела;
- `profile.html` и `settings.html` - профиль и настройки;
- `owner.html` - owner-панель;
- `schedule-lab.html` - owner-only учебный табель.

## Как работать с кодом

- Работать прямо в репозитории и делать точечные изменения в существующей архитектуре.
- Не ломать стабильные HTML-маршруты, DOM `id` и формат сохраненного `timesheets.payload` без необходимости.
- Общие запросы Supabase держать в `js/db.js`, общую авторизацию - в `js/auth.js`.
- Повторно используемую логику выносить в небольшой модуль только при реальной пользе.
- Не возвращать удаленные чат, голосование, задачи, инструкции ЕГАИС, мини-игру и Excel-выгрузку без прямого решения владельца.
- Не коммитить сгенерированный каталог `www/`, секреты, пароли, приватный VAPID-ключ и реальные служебные UUID.

## UI / UX

Сохранять текущий визуальный язык:
- фон `#0b0d0f`, панели `#15191d`, текст `#f1eee8`;
- винный, стальной и золотой акценты;
- Anticva для крупных заголовков, Inter для интерфейса;
- плотные рабочие экраны, скругления преимущественно 5-9 px;
- общие header и footer из `js/nav.js` и `js/footer.js`;
- обязательная проверка iPhone safe area, мобильного переполнения, клавиатурного фокуса и `prefers-reduced-motion`.

Не возвращать старый темно-синий дизайн, Tailwind CDN, декоративные карточки внутри карточек, крупные скругления и фиолетово-синие градиенты.

## Больше не предлагать

Этот список является постоянным ограничением. Когда владелец пишет «Больше не предлагать», добавлять соответствующий пункт сюда.

- Автоматическое составление или автоматическое заполнение табелей.
- Шаблоны смен, пресеты смен, массовое применение готового графика и другие замаскированные варианты автоматизации заполнения табеля.

Исключение: по прямым запросам владельца реализованы ограниченные инструменты для стабильных графиков. Их действующие правила описаны в `SCHEDULE_TOOLS_PLAN.md`. Не предлагать новые варианты автоматизации без запроса.

Также без нового запроса не предлагать:
- открывать журнал изменений табеля кому-либо кроме owner;
- отдельную кнопку отмены последнего действия вместо работающего `Ctrl+Z`;
- проверку табеля, которая пытается угадывать производственный контекст;
- виртуализацию строк админ-табеля без подтвержденной проблемы производительности.

## Авторизация и роли

- Основные роли профиля: `user` и `owner`.
- Редактор отдела хранится в `department_editors`, а не в `profiles.role`.
- Подтвержденный руководитель определяется серверным признаком `department_editors.is_leader`, а не выбранной должностью.
- Owner-страница обязана проверить сессию, профиль и `profile.role === "owner"`.
- Клиентский интерфейс никогда не считается достаточной проверкой доступа: привилегированные действия выполняются через защищенные RPC или Edge Functions.
- Удаление сотрудника из отдела не удаляет аккаунт и историю табелей.

Обязательные поля профиля для доступа к рабочим разделам: ФИО, должность, пол, филиал, дата трудоустройства и оклад. Пароль не сохраняется и не журналируется; локальная политика требует минимум восемь символов.

## База и безопасность

- Все SQL-изменения добавлять отдельными нумерованными файлами в `supabase-sql/`.
- Предпочитать idempotent SQL и `create or replace function`; `drop` использовать только при явной необходимости.
- После RPC выполнять точечные `revoke`/`grant`, проверять `security definer`, `search_path` и RLS.
- Service-role используется только серверными функциями.
- Пользовательский текст выводить через `textContent`, URL проверять по разрешенным схемам и origin.
- Денежные данные не показывать в обход существующей PIN-защиты.
- Журналировать только существенные программные ошибки; сетевые сбои, отсутствие VPN и отмененные запросы не считать ошибками приложения.
- Инструкции Edge Functions находятся в `EDGE_FUNCTIONS.md`, порядок SQL - в `SUPABASE_SQL.md`.

## Табель и расчеты

Главная формула находится в `js/calc.js`.

Основные правила:
- премия 35%, налог 13%, ночная надбавка 40%;
- праздничные часы считаются отдельно как двойная оплата;
- вредность грузчика - 4%;
- женская норма филиала CHATEAU ALVISA - 7,2 часа в рабочий день;
- годовой лимит переработки пока 120 часов;
- сохраненный `moneySnapshot` приоритетнее текущего оклада;
- подтвержденные фактические выплаты приоритетнее авторасчета в истории;
- сутки не могут содержать более 24 часов;
- коды отсутствия и увольнения нельзя перезаписывать инструментами графика.

Автоматические инструменты общего табеля должны учитывать подтвержденного руководителя, дату приема, увольнение, отсутствия, запрет ночных смен, персональную норму, праздники и сокращенные дни. Полные правила находятся в `SCHEDULE_TOOLS_PLAN.md`.

Производственный календарь находится в `js/productionCalendar.js`. Проверенный дагестанский снимок используется для доступного периода, остальные даты загружаются через API с консервативным резервом без выдуманных переносов.

## Зафиксированные решения

- Общий табель сохраняется через защищенный RPC и пишет компактный owner-only журнал изменений.
- Кеш графика предназначен только для чтения; при недоступной базе нужно показать дату кеша и запретить отправлять его как новые данные.
- Чек-листы хранят завершенную историю и не удаляются автоматически.
- Push-получатели определяются сервером, а не передаются клиентом.
- Screen Wake Lock зависит от поддержки браузера и не обходит системную политику устройства.
- Распознавание расчетного листка выполняется локально и переносит значения только после проверки и подтверждения пользователя.
- Фактический размер базы получает owner-only RPC; предупреждения показываются с 70%, критический статус - с 80% лимита.

## Обновления

В `updates.html` добавлять только заметные пользователю изменения. Внутренний рефакторинг, owner-only инструменты и служебный SQL не публиковать без прямой просьбы. При новом публичном обновлении менять `CURRENT_UPDATES_VERSION` в `js/nav.js`.

## Проверка изменений

Проверки должны соответствовать масштабу правки:
- после обычного изменения запускать только связанные тесты;
- после изменения JS проверять синтаксис затронутых файлов;
- всегда выполнять быстрые `git diff --check` и `git status --short` перед коммитом;
- полный `npm run check` запускать после крупного рефакторинга, перед важным релизом или отдельной итоговой проверкой раз в несколько дней, а не после каждой небольшой правки;
- сборку Android запускать только при изменениях мобильного scaffold, путей ассетов или Capacitor-конфигурации.

Если владелец просит коммит и push, выбрать короткое сообщение по смыслу, выполнить `git add`, `git commit`, `git push`, затем проверить синхронизацию ветки.
